Payment Idempotency Protection & CAS Distributed Mutex

Topic: Distributed Systems & Concurrency Invariants Double Debits: 0 (100.0% Verified) Author: Samrudh Dwivedula

In automated payment recovery, the single most catastrophic risk is the double-debit bug: charging a customer twice for the same purchase because parallel webhook retries, automated cron jobs, or browser re-submissions triggered concurrent recovery charges.

The Concurrency Challenge

When a payment gateway experiences intermittent network timeouts, it regularly dispatches duplicate failure webhooks within milliseconds of each other. If an automated recovery agent does not implement atomic synchronization, two independent worker threads will simultaneously initiate a recovery transaction on alternate rails.

The Compare-And-Swap (CAS) Mutex Mechanism

OmniRevive-OS solves this using a distributed Compare-And-Swap (CAS) atomic lock pattern backed by Redis with a sliding TTL:

def acquire_recovery_lock(tx_id: str, client_id: str, ttl_seconds: int = 15) -> bool:
    lock_key = f"lock:recovery:{tx_id}"
    # Atomically set key only if it does NOT already exist (NX)
    acquired = redis_client.set(lock_key, client_id, nx=True, ex=ttl_seconds)
    return bool(acquired)

Execution lifecycle:

  1. Lock Acquisition: Worker 1 attempts to set lock:recovery:tx_123 with nx=True. Redis returns OK.
  2. Collision Rejection: Worker 2 arrives 20ms later and attempts the same operation. Redis returns nil. Worker 2 immediately halts execution with IDEMPOTENCY_COLLISION_CONTAINED.
  3. Atomic State Transition: Worker 1 executes the single recovery charge, updates the state to RECOVERED, and records the receipt in the SHA-256 Merkle audit chain.
  4. Safe Release: The lock is released via a Lua script verifying that the releasing client matches the original lock owner, avoiding accidental lock releases by slow workers.
